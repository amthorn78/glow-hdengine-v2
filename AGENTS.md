# AGENTS.md — Glow HD Engine (agent rules)

## Canon-first rule (every agent, every task)
- PF-Canon in `docs/pfcanon/` governs all work in this repository. A change's in-flight documents in `docs/ephemeral/` (its approved Specification, its approved Plans, and the decisions in its reviews and Product Owner dispositions; file names start with the change ID) are canon for that change: they modify canon during the implementation flow. A Specification is a permanent governed record; a Plan is working direction. Where an in-flight document conflicts with PF-Canon, PF-Canon governs unless an applicable PF10 rule supersedes it for that exact scope, or a formally approved bounded Product Owner rescope supersedes it for the exact decision it adjudicates. Prompts, handoffs and skills do not list which documents apply; finding them is the agent's job.
- At the start of every task, and whenever its subject changes, search all of `docs/pfcanon/`, and the change's documents in `docs/ephemeral/`, for material relevant to the task: its terms, the surfaces and environments it touches, and the section headings (for example `grep -n -i -E '<terms>' docs/pfcanon/*.md docs/ephemeral/<CHANGE-ID>-*.md`). Read every governing section the search finds in full, and apply it. Use the current version of each in-flight document, never a superseded or rejected one. Search; do not load all of canon into context.
- Do this before planning, authoring, reviewing, deciding or asking the Product Owner anything. A review checks the work against the canon the reviewer has read, not only against code.
- Never ask the Product Owner a question canon answers. Ask only when the search finds canon silent or in conflict, and name the sections searched.
- Record the PF titles and sections relied on in each artifact you produce. Never state or imply that work conforms to canon that was not read.

## PF10's authority in the canon
- PF10 is the canonical override and amendment mechanism for the PF document set. Where PF10 establishes a later rule, exception, clarification, supersession or override that conflicts with earlier PF canon, the applicable PF10 rule governs.
- Existing PF canon documents are not rewritten merely to incorporate those later changes. Further canonical changes are normally introduced through a new PF10 addendum rather than by editing the affected earlier canon.
- Search all of PF10 for every rule relevant to the task; a later PF10 rule governs over an earlier one only where their scopes overlap.

## PF canon is read-only unless the prompt explicitly directs a change
- Agents must not modify any PF canon document, PF10 included, unless the current prompt explicitly directs the agent to modify that particular file. A general instruction to update documentation, reconcile canon, fix inconsistencies, implement decisions, clean up files or maintain documentation is not authorization.
- Without that explicit direction: do not edit an existing PF canon document; do not silently correct, modernize, reconcile or rewrite canon; do not patch conflicts in an earlier PF document; do not alter canon because implementation or review shows a rule is outdated or inconsistent.
- When canon appears to conflict, determine the rule that governs the work, including whether PF10 already establishes a controlling override. Do not resolve the conflict by modifying canon. If canon itself needs a change, report or propose it.
- When the prompt explicitly directs a canonical change, make only that change. A new override, amendment, clarification, exception or supersession of earlier canon is normally made as a new PF10 addendum. When adding, replacing, renaming or removing a directed PF file, preserve all unrelated content and report the resulting commit.
- PF documents other than PF10 never cite PF10 by section, addendum number, heading, paragraph or version; PF10 is designed to keep growing, so such references become brittle. PF10 addenda may cite other PF10 addenda.

## Codex reasoning and execution posture
- For every complex task, use the most capable reasoning model available and the highest reasoning-effort setting available (for example, `model_reasoning_effort: high`). Never reduce reasoning effort for a complex task to optimize latency or cost.
- Treat implementation, debugging, architecture, security, data migration, release, evidence, and multi-file work as complex unless it is clearly mechanical and low risk.
- Low reasoning effort is permitted only for clearly trivial work such as formatting, typo fixes, or minor mechanical cleanup that requires no substantive judgment.
- Prefer a pragmatic execution style: prioritize correct, clean, reviewable diffs and appropriate verification over verbose process narration.

A plain `out=$(producer)` does preserve the producer's status, so this is a warning about those wrapping contexts, not about command substitution as such. Cite an exit code only from a capture that carries the producer's own status; where it does not, re-run only if the command is safe to repeat, and otherwise withhold the exit-code claim.
