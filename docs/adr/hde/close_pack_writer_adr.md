## Problem

An ordinary Close Gate needs a close report and manifest that canon can accept, written from tracked inputs, plus same-run evidence of the close workflow. HDE-EPIC040 showed that neither existed (closure evidence record CLOSE01, findings B-1 and B-2):

- B-1. The generic writer `tools/qa/generate_epic_close_pack.py` was made neutral on purpose by HDE-EPIC039: a closed vocabulary of four headings and ten fixed body lines, five fixed nonclaims, Epic identities only. It cannot write the required heading `QA Rails — Open/Close (Final PR)`, the acceptance pointers, a binary decision, deferrals, later-drain statements or a manifest `key_outputs` map, and one of its fixed nonclaims ("No QA PASS, acceptance, or token satisfaction is claimed.") contradicts a `SATISFIED` close.
- B-2. Every admitted evidence home under a change's QA root is a check listed in `qa_step_logs_manifest.json`. Recording the close run there reopens an approved QA manifest after the verdict.

HDE-EPIC040 then closed by Product Owner-authorized exceptional closure, as HDE-EPIC038 had before it.

## Decision

1. **A second source schema version.** `schemas/close_candidate_source.v2.json` is a closed schema for one Epic (`HDE-EPICNNN`) or CRD (`HDE-CRD-NNNN`, four or more digits). `schemas/epic_close_candidate_source.v1.json` stays, unchanged, for history; a v1 source keeps the v1 model, refusals and output bytes.
2. **One writer, kept at its registered path.** `tools/qa/generate_epic_close_pack.py` selects the model by the source's `schema_version`. Its CLI, closed-rails refusal, clean-tree and tracked-input rules, manifest-last publication, `manifest → report → manifest` reading and non-writing check mode are unchanged.
3. **Paths of record.** An Epic writes `audit/EPIC-NNN_close_report.md` and `audit/EPIC-NNN_MANIFEST.json`. A CRD uses its ID as the prefix (`audit/HDE-CRD-NNNN_close_report.md`, `audit/HDE-CRD-NNNN_MANIFEST.json`) and its lower-case ID as the directory form (`hde-crd-nnnn`). The candidate source for HDE-CRD-0002 is `audit/HDE-CRD-0002_close_candidate_source.json`.
4. **What the v2 report carries**, each part rendered from a structured source field: the verbatim `QA Rails — Open/Close (Final PR)` heading; the "Acceptance and evidence pointers" list; the binary `SATISFIED` / `NOT SATISFIED` closure decision with its posture, review-trace-only; an exact-source acceptance section that binds each criterion ID to one of the approved Specification's requirement IDs the source records, to tracked evidence and to a result and limitation, and that names the authorized decision, the final QA report the source records, and its verdict (Change Process Guide §3.5.2.1; PO-35-20). Each `MET` criterion binds the primary of a check that the QA step-logs manifest records as `PASS` and whose recorded QA plan mapping names the criterion (PO-35-21). Every criterion ID, and every criterion a recorded QA plan check maps, must be one of the recorded requirement IDs (`REQUIREMENT_ID_UNBOUND` otherwise). `SATISFIED` needs a recorded QA report verdict of `PASS`, an acceptance row for every recorded requirement ID, every row met, no follow-up, and a bound QA step-logs manifest, in the pinned ledger format, that records every check of the recorded QA plan as `PASS`, or as `TOOLING_BLOCKED` with a closure-override gap that names it, each status agreeing with its tracked primary's header; `NOT SATISFIED` needs at least one follow-up; the coverage ledger, listing every planned check in plan order with a coverage status (`PASS`, `FAIL`, `BLOCKED` or `NOT_RUN`) and its closeout impact; delivered scope; the PR-to-deliverable allocation; the reuse boundary; deferrals, each with a drain target that names the change kind's register by PF title and one of its headings, or with an ADR status and rationale, and in both forms the deferral's ID occurs in the drain-targets ledger; later-drain statements, their action and readiness in the fixed vocabulary of HDE Schemas & Artifacts §1.2 and their epic-close expectation in HDE Governance's three values (`at epic close`, `after an additional PR or OPS slice`, `after a separate canon-only drain step`), stated as support records only; the tracked-issue mapping in HDE Governance's literal `ADR status line:` field, each item an ADR status whose ID occurs in the drain-targets ledger (Change Process Guide §3.5.2.1, form (b); PO-35-11); the ADR block that Change Process Guide §3.5.4 requires; follow-ups; superseded artifacts; the QA RCA, embedded or bound as `audit/<prefix>_QA_RCA.md`; a "Key outputs" section; the close-pack verification statement; the source bindings; four nonclaims that are true of any close, and HDE Governance's no-over-claim line: the close pack establishes no formal close-pack completion, merge provenance, board state, PO closeout, Isis terminal closure decision or formal Ops action. Free text is limited to single neutral lines in named fields.
5. **What the v2 manifest carries.** A `key_outputs` JSON object whose values are repo-relative path strings: at least the close report, the close manifest, the doc-delta ledger, the drain-target ledger and the QA step-logs manifest. It points to the report by SHA-256 and size and carries no digest of the Index, a path proof, the orientation output or the close-run family. Every key output other than the close report and the close manifest is also a bound tracked evidence input, so its digest is recorded (`OUTPUT_BINDING_MISMATCH` otherwise).
6. **Feedback-freedom kept.** The v1 feedback-dependency refusal applies unchanged to every v2 causal value but one, a recorded QA primary path (below). Requirement and acceptance text is bound by reference (the requirement ID the source records, and the criterion ID), never copied into a causal field. Two of HDE-CRD-0002's own requirement rows (S06, S11) contain words the refusal rejects; binding by reference lets the close record them without weakening the refusal. The one value the refusal does not read is an evidence path in the QA-primary form `audit/qa/<change-dir>/checks/<check_id>/primary.log` of the source's own change, and it stands only when the bound QA step-logs manifest records that primary (`FEEDBACK_DEPENDENCY_PROHIBITED` otherwise). Such a path names a check of the approved QA plan, not a hosted result, and the primary is bound by its digest as before; HDE-CRD-0002's QA plan maps S06 only to `qa-03-attestation-debian`, so without it no source could bind S06's evidence (close-tooling defect B-4). For the same reason the refusal does not read a value that is exactly one of the source's recorded QA plan check IDs. The v2 writer also refuses, as causal inputs, the Index trio and its sentinels, every `.path_proof.txt`, the orientation output, every path under `audit/qa/<change-id>/close/`, `catalog/manifest.json`, and every path under `docs/ephemeral/` or `docs/pfcanon/`.
7. **A post-verdict close-run family** for admitted CRDs: `audit/qa/<crd-id>/close/<check_id>/primary.log` with a path proof, published only by the canonical updater through `tools.evidence.update_evidence_index.publish_crd_close_run_family(config, results, *, captured_at_utc=None, coherence_verifier=None)`, a Python API like `publish_crd_check_family`. Each primary is a PF27 v2 step-log header rendered from the captured command, exit code and output of one close-run check. The family is never listed in `qa_step_logs_manifest.json`; the entrypoint writes neither that manifest nor any `checks/` primary. It requires the CRD's recorded QA family to exist. The given results replace the whole family inside one recovery transaction. HDE Build Notes addendum 2.15 introduces this family, with a membership exception for `close/` only.
8. **Absent-tolerant CRD close-pack rows** in the Human Index for every admitted CRD: neither file present, no rows; both present, one row each (`hde_crd_nnnn.close_report`, `hde_crd_nnnn.manifest`, with `crd_id`); one present, or a row whose file is gone, refused. Until a CRD closes, the Index is unchanged.
9. **The ADR block.** The v2 source carries a required, non-empty list of ADR-block decisions, each with a label, a statement, the decision point, the options considered when more than one was real, the bounding PF canon by title, the final decision, whether it becomes canonical or stays change-specific, and the Doc Delta targets by PF title. At write time every PF title must name a PF-Canon document tracked at HEAD. An optional closure-override entry enumerates each accepted gap with the `TOOLING_BLOCKED` check it accepts, its bound evidence basis and its drain targets. The report renders them as an "ADR block" section with titles-only canon references.

Dependency direction (no cycle):

`tracked causal inputs → close report and manifest → Index`; `close-run primaries → Index`

No byte the Index binds depends on the Index, and no hosted run writes a byte the final state needs.

## HDE-EPIC039's neutral writer, weighed

HDE-EPIC039 kept the writer ignorant of the evidence graph and of any claim, so that a candidate could never certify itself. S21 reverses only the second half of that choice: the v2 report states the closure decision and its posture because canon requires it, and it claims nothing its bound tracked inputs do not record. Kept from HDE-EPIC039: the single writer, its CLI and rails, tracked inputs at a clean HEAD, report first and manifest last, the manifest-to-report read, mixed-state refusal, symlink-byte verification, the non-writing check and the absence of hosted feedback. The v2 block names updater outputs and the close-run family only to refuse them as inputs, and binds the QA step-logs manifest as a tracked input and names it as a canonical pointer.

## Alternatives considered

- (a) Extend the generic writer and admit a post-verdict family: this decision.
- (b) A separate governed close-report writer beside the neutral one: two writers for one artifact family, and the same canon change.
- (c) Let the close PR add a manifest check after the verdict: reopens an approved QA manifest (CC-2), rejected.
- A canon change that drops the close-report requirement, or keeping exceptional closure for every change: weighed by the Product Owner on 2026-10-20 against the observed HDE-EPIC040 and HDE-EPIC038 closures; the Product Owner chose the writer (WU-PR-07 business case).

## Stated limits

- The closure-decision posture is exactly `review-trace-only` (PO-35-20); another posture needs a later schema version. A close pack cannot prove its own formal completion before its close PR merges, and canon marks that state not proven unless it is directly proven. PO closeout is the Product Owner's own action, which a close pack supports and never states (Change Process Guide; PO-35-14).
- The authorized decision is the final QA report the source records in `planning_records`, with its verdict in `qa_verdict`, an upper-case token such as `PASS` or `FAIL`. `SATISFIED` needs `PASS`. The writer reads no QA report.
- The planning records are texts the close agent writes from the planning documents when it writes the source, each naming the document's identity and SHA-256 so a reader can match the archived document. The writer checks their form, not that they agree with the documents; the close review does.
- A `MET` criterion must bind the `primary.log` of a check that the QA step-logs manifest records as `PASS`, and that check's recorded mapping in `qa_checks`, which the close agent takes from the check's first `Surface / D-goal mapping:` line in the QA plan (Plan Templates) with any `A to B` range written out, must name the criterion (PO-35-21; `ACCEPTANCE_EVIDENCE_UNBOUND` otherwise). A `TOOLING_BLOCKED` check accepted under a closure override is not `PASS` evidence (Change Process Guide §3.5.4, "No posture-only PASS"). A criterion that the plan maps to no check cannot be `MET`, as HDE-EPIC040's documentary K040-REQ-001 and K040-REQ-002 are not. The writer reads the plan's mapping as the approved plan's claim and does not judge whether the check's command proves the criterion.
- A closure override accepts only a check that the QA step-logs manifest records as `TOOLING_BLOCKED`, each check named once (PO-35-13; `CLOSURE_OVERRIDE_INVALID` otherwise). A `FAIL_BEHAVIOR`, `FAIL_TOOLING` or `PARKED` check, and a planned check the ledger does not record, block `SATISFIED`.
- The QA plan's checks are the source's `qa_checks`, in plan order, each check ID once (PO-35-18; `QA_PLAN_STEPS_ABSENT` otherwise); the writer reads no QA plan. Every check in the QA step-logs manifest must be a planned check (`QA_COVERAGE_INVALID`). The coverage ledger maps `PASS` to `PASS`, `FAIL_BEHAVIOR` and `FAIL_TOOLING` to `FAIL`, `TOOLING_BLOCKED` and `PARKED` to `BLOCKED`, and an unrecorded check to `NOT_RUN`. It records no deviation or mismatch text; that belongs to the QA RCA.
- At write time only, a PF title is read from a `docs/pfcanon/` file name tracked at HEAD: the part after the optional PF number and the optional `Canon` or `Reference` kind, and before the optional version, where hyphens, spaces or both separate the parts. Hyphens are read as spaces, a run of spaces as one, and `&` as `and` (PO-35-16). Every tracked PF-Canon file gives a title, including those named with spaces (CX7-19). Each later-drain canon home, each ADR decision's bounding canon and Doc Delta target, and each accepted gap's drain target must match one (`PF_TITLE_UNKNOWN` otherwise).
- A deferral's drain target names the register by PF title, `HDE CRD Records` for a CRD or an `HDE Build Checklist` title for an Epic, and gives the full text of one of its Markdown headings. At write time the title must name exactly one PF-Canon file tracked at HEAD, whatever its version, and the heading must occur in it (PO-35-17; `DEFERRAL_POINTER_UNBOUND` otherwise). The writer checks that the heading exists, not that the section will hold the drained item. The heading is a causal value, so the feedback-dependency refusal applies to it unchanged (decision 6): a heading with words that refusal rejects, as three PF09.6 headings have, cannot be named, and such a deferral takes the ADR-status form.
- Every delivered-scope item appears in at least one allocation row, and every allocation row names a delivered-scope item (PO-35-19; `ALLOCATION_INCOMPLETE` otherwise). A slice is a PR number (`#<n>`), a work-unit ID (`WU-…`), or an Epic plan's PR slice (`PR<nn>`, with an optional lowercase letter, as HDE-EPIC040's plan names them). The reuse boundary is required and may be empty, in which case the report states `None recorded.`.
- A bound QA RCA must be `audit/<prefix>_QA_RCA.md`, using the close report's own prefix (Change Process Guide §0.4.1.2; `QA_RCA_UNBOUND` otherwise).
- The writer checks the structure of the narrative fields only: delivered scope, limitations, follow-ups, deferral rationales, the ADR block's texts, accepted-gap texts, the reuse boundary and the RCA. It does not judge whether their content is true or complete; the close review does.
- Requirement coverage is checked against the requirement IDs the source records (`requirement_ids`), which the close agent takes from the approved Specification; the writer reads no Specification.
- A tracked issue maps only through an ADR status (PO-35-11). The register-pointer form (Change Process Guide §3.5.2.1, form (a)) is refused by the schema, because no PF09 or PF30 file cites a TI ID, so no pointer can be shown to demonstrate that issue's closure.
- The implementation plan is a record text in `planning_records`; the source names no plan path. Every pointer names a tracked file or a directory holding one, except a CRD's close-run directory, which is written after the verdict (`POINTER_UNRESOLVED` otherwise).
- The supporting ledgers meet a pinned minimum content (PO-35-12), and anything else is refused:
  - The doc-deltas ledger states exactly `Doc Deltas: None` (HDE Mechanics Guide) or enumerates its deltas as Markdown list items, never both; otherwise `DOC_DELTAS_INVALID`.
  - A tracked QA-root copy `audit/qa/<change-dir>/00_meta/doc_deltas.md` must be byte-identical to the doc-deltas ledger (HDE Schemas & Artifacts §1.2); otherwise `DOC_DELTAS_INVALID`.
  - The drain-targets ledger states `Drain Targets: None` exactly when the source has no deferral and no tracked issue; otherwise `DRAIN_TARGETS_INVALID`. That literal is the Product Owner's pin, mirroring the Mechanics Guide's form, because §1.2 requires an explicit empty indication without giving one.
  - The writer checks this structure only. It does not judge whether each listed entry is a true canon delta.
- The QA step-logs manifest is read in one pinned format, the flat mapping the canonical QA harness writes (`check_id` to exactly `check_id`, `log_path` under `audit/qa/<change-dir>/checks/<check_id>/primary.log`, `status`), in the harness's own bytes: strict JSON, sorted keys, compact separators, lowercase check IDs and one final LF, so a duplicated or reordered key cannot stand (PO-35-10); any other ledger, including an empty one, is refused (`QA_LEDGER_INVALID`), and `SATISFIED` needs every recorded status to be `PASS`. Each entry's `primary.log` must be tracked and open with a PF27 v2 step-log header that meets the canonical QA harness's whole header contract (its fields, command and exit-code consistency, PASS causality, evidence including the primary itself, and for a CRD the canonical bytes) and whose `check_id` and `status` match the ledger (`QA_LEDGER_INVALID` otherwise); the primaries' digests are recorded in the manifest and under Source bindings. The writer restates that contract, because its imports stay the standard library and `jsonschema`, and a test holds the two in agreement. Beyond the header, the writer reads only the token nonclaim line; it does not judge the rest of a primary's body, which the harness renders from the captured result.
- No Epic close-run family is admitted. An Epic close run needs its own explicit admission later, as each CRD needs its row in `ADMITTED_CRD_QA`.
- A later Epic's v2 close pack is written and checked by the writer, but its Index rows need that Epic's own registration, as for earlier Epics.
- As in v1, an earlier commit's ID written without the refusal's trigger words is not refused; the current HEAD's ID is.

## Epic-only identity inventory (HDE Schemas & Artifacts §1.2)

## Nonclaims
