Observed behavior: after importing the actual PR03 core, a temporary synthetic complete release was admitted and computed successfully. In that temporary fixture only, `signals.py` was changed from addition to subtraction and its exact source bytes and manifest identities were coherently regenerated through the existing fixture owner. The changed Python source compiled successfully. Admission then succeeded with a different release identity, but `compute_core` still executed the previously imported addition implementation, returned identical signals/categories, and labelled the result with the altered release ID. Expected behavior is an owning fail-closed refusal before a result can be associated with non-equivalent executing mechanics.

This is an implementation defect in PR03's integration of newly active mechanics with release identity. `engine/core/core.py::_validate_bundle` checks that the bundle's recorded source identities agree with its manifest entries; that does not establish equivalence to the loaded executable code. The accepted `_admission_execution_provenance` owner in `engine/config/registry_loader.py` intentionally covers four existing modules: the registry loader, serializer wrapper, stable serializer, and category registry. The accepted `_validate_executing_admission_sources` passively compiles their captured bytes and compares their top-level code objects to retained execution provenance. The four newly active PR03 modules are not in that bounded owner set. Other Python release members receive syntax checks without that executing-code comparison.

The four missing mechanics owners are `engine/core/core.py`, `engine/magic10/composite.py`, `engine/magic10/signals.py`, and `engine/magic10/calculators.py`. The defect was already present in source tree `4af351d6f7347541b9853927bf5098299adcc81f` before the commit-message correction. Rewording the commits changed no source bytes and did not create this code behavior. It triggered another configured review that detected it.
