## 4. Material finding: supported no-user input resolution is not yet designed

### F040-IA30-01 — Complete chart and canonical identity must reach the shared evaluator

**Severity:** material Plan implementability and proof gap. **Owner:** same whole-change IA; implementation ownership remains PR04, with its existing downstream evidence/dependency obligations. **Required deadline:** complete successor design before Plan approval, not discovery deferred to PR implementation.

**Author intent:** Plan §5.8 expressly preserves existing admin/CLI and birth-only workflows, rejects a new caller UUID requirement, requires complete canonical projections and prohibits hash-based scoring. That is the correct intended boundary.

**What the complete design actually supplies:** the production Reader has a concrete exact UUID/current-view query and side-effect rules. The birth-only branch has only the instruction to reuse a sanctioned layer and return a typed failure if it cannot supply a projection. PR04 names existing components, but does not define how that branch obtains Gates, how its derived identity reaches the canonical UUID requirement, or what existing no-user success means after removal of the placeholder path. Its listed positive/adverse proof is dominated by resolved UUID/Reader cases.

**Observed before-state:**

1. `engine/compat/compute.py::_resolve_party` returns `{"person_uid": birth_uid}` immediately for a complete birth tuple with no user ID. `_derived_birth_uid` produces a `birth-` identifier; that branch supplies neither a resolved chart nor a canonical UUID. Other compat resolution paths also reduce a resolved person to UID-only data.
2. `engine/cli/main.py::_person_and_chart_from_payload` retains Type but discards Gate data; `_derive_uid` can produce a `cli-` identifier. The existing vendor/DB flows are distinct acquisition paths and must keep their controls when adapted.
3. `engine/bodygraph/ingest.py::resolve_db_user_id` is an available deterministic internal alias bridge. It can resolve non-UUID inputs to UUID5; the repository explicitly limits its role to an internal durability anchor. This disproves any claim that internal identity resolution is wholly unavailable. It does **not** by itself retrieve or validate Gates, establish the no-user chart lookup, or authorize UUID5 on production Reader. The Plan must name the intended lawful use and projection handoff.
4. `tests/compat/test_conjunction_no_user_boundary.py` presently passes birth-only inputs, closed rails and a lookup returning None, then checks synthetic IDs and AB/BA bytes. It therefore demonstrates the old UID-only behavior, not a successful complete Gate-based boundary. The existing `test_showcompat_sources.py` fixtures also include Type-only or empty-Gate charts and old wrapper expectations. Merely retaining those test names does not specify the new positive proof.

**Controlling basis:** approved Specification K040-REQ-001/004/007/008/011/012, AC040-04/07/08/09; PF02's sanctioned birth-only boundary and separate proof classes; PF01's valid Gate/identity boundary; PF05's complete internal result and input/refusal contracts; current IA-30's implementability and independent reader-inference requirements.

**Consequence:** competent implementers could choose incompatible solutions: derive identity differently, require caller UUIDs, obtain charts through different acquisition paths, or fail every legitimate birth-only request. A generic typed-refusal instruction prevents fabricated scores but cannot establish preservation of the supported successful input class. This is a cross-component input/projection decision, not a request for detailed per-line code or a new public feature.

**Bound:** this finding does not require success from a birth tuple when no lawful chart source exists under the active rails. Closed-rails missing-chart refusal is correct. It requires a concrete lawful success route when complete chart data is available, explicit refusal when unavailable, and separate proof of each. It does not require a vendor call, database mutation, new public field, public endpoint, empirical research, second calculator or extra work unit. It does not import HDE-SEPA006’s separate non-BodyGraph loader relocation/caller migration into this Epic; only the already selected Magic10 consumer projection dependency is being corrected.
