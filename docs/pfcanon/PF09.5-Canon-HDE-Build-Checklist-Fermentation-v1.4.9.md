## **0.1 Scope**

This phase covers first contact with live use. From a software development perspective, Fermentation begins when the integrated product meets real users or real operational pressure: usage patterns are observed, critical bugs are stabilized quickly, instrumentation becomes central, and the product starts changing in response to lived reality instead of planned intention alone. From a planning perspective, this document should track the work that captures live signal, support loops, and meaningful adaptation, including the disciplined handling of unexpected behaviors, emergent use cases, and feedback that should reshape priorities. It is not the place to dismiss real-world feedback as noise or to prioritize speculative expansion over learning and stability.

Build-only, dependency-ordered checklist of **development and operations work** required to reach and maintain a stable production run of the HD Engine. PF09 tracks only tasks and subtasks that require **dev or ops engagement**, meaning they produce or change at least one of the following:

* Code (engine, CLI, transport, harnesses, tooling)  
* Tests (unit, integration, transport proofs, determinism checks)  
* Runtime configuration or deployment behavior  
* Infrastructure or operator actions (secrets, environment provisioning, migrations, access controls)  
* Required runnable evidence captures that are necessary to validate the above changes

PF09 explicitly excludes **documentation-only** and **process-only** work, including templates, prompt guidance, playbooks, ledgers of already-completed checks, historical reports, and canon alignment text changes that do not require corresponding dev or ops work. Evidence is recorded only as acceptance artifacts for in-scope tasks. PF09 MUST NOT contain standalone “evidence ledger” rows.

Checklist items are organized by seven alchemical phases (Calcination, Dissolution, Separation, Conjunction, Fermentation, Distillation, Coagulation). Each task/subtask is tagged with a tracking ID of the form `HDE-<PHASE><NNN>` or `HDE-<PHASE><NNN>.<m>` (for example, `HDE-CALC001`, `HDE-CALC001.1`). These IDs are for traceability only and do not imply priority or status.

This document MUST include “jobs to be done” that require dev or ops engagement, including:

* Development  
* Implementation  
* Operations

## **0.2 Conventions**

**Statuses** are canonical and use the following values only:

**Done** — Required behavior is implemented and evidenced for the slice this row covers.

**Partial** — Some but not all of the required behavior or evidence for this row is implemented; notes explain the gap.

**Not done** — Behavior is specified in canon, but implementation and/or evidence are still absent.

**Consolidation pending** — Behavior exists in multiple slices and must be consolidated under a single epic or harness before it is treated as Done.

**Optional** — Non-blocking work that may be implemented without gating releases.

**Pending Revalidation** \- Needs revalidation per PO

 **Deferral (closure-safe; no new status enums).** If a task is intentionally not completed for the current epic and is being pushed to a future epic, keep the **Subtask status** within the existing allowed values (typically **Not done** or **Optional**) and record deferral explicitly in **Notes** using this minimal form:

* `DEFERRED → <future-epic-id or backlog stub> — <short reason>; not a close blocker for <current epic-id>.`

This makes the remaining work visible without creating a false “failed close gate” interpretation when the epic record explicitly allows deferral.

**Deferred-issue posture (acceptance artifacts; EPIC022 bridge).** When an epic explicitly closes with deferred QA issues, those issues MUST be recorded as deferred in the acceptance artifacts and MUST NOT be claimed as satisfied.

For token drift deferrals: do not maintain “known unregistered tokens” lists in epic records; treat the registry-validation output as the authoritative evidence of whether a token is claimable.

**Supportable vs drained status notes.** When Notes need to distinguish a status that repo evidence supports from a status already recorded in PF09, use explicit wording and do not blur the two states.

* `Supportable from repo evidence:` repo evidence supports the status change, but PF09 has not yet been updated.  
* `Drained into PF09:` PF09 has already been updated and the recorded status here is canonical.

Do not write notes that make a supportable status change read as if it has already been drained into PF09.

**PF09 accountability for backlog and future work.** Backlog, future, deferred, optional, follow-up, remediation, runtime, adapter, vendor, QA, OPS, evidence, and product-task items are scheduling or scope postures, not PF09 escape hatches.

Any task-like item that affects implementation, QA, OPS, runtime behavior, evidence behavior, vendor behavior, architecture, or product behavior MUST resolve to exactly one of:

* Mapped PF09 task/subtask. Use when the relevant phased PF09 task/subtask exists.  
* PF09 gap. Use when the work is legitimate phased build work but no current phased PF09 task/subtask accounts for it.  
* Documentation/status drainage only. Use only when the item is a document/status reconciliation task and not implementation, QA, OPS, runtime, evidence, vendor, product, or architecture work.  
* Out of HDE phased build scope. Use only when the item truly does not belong to the HDE phased build checklist.

If a PF09 parent task exists and relevant subtasks exist, subtask-level mapping is required. Parent-task-only mapping is invalid unless no relevant subtask exists.

**Rendered escape artifacts and plan-syntax posture:** PF09.5 task, subtask, status, path, token, artifact-key, command, plan-review, and evidence-review posture must distinguish rendered display text, plan examples, and operational syntax from raw source identity and material proof obligations.

A rendered escape character in assistant-visible output, rendered Markdown, copied chat text, preview panes, or review prose is not evidence of a PF09 source defect by itself. Treat added backslashes or escape characters as display-layer artifacts unless raw source inspection proves the character is present in the actual source and changes executable, governed, canonical, or semantic identity.

Plans, QA steps, implementation plans, remediation plans, redline prompts, Codex prompts, and closure-review artifacts are not execution artifacts. Command exactness, paste-readiness, heredoc form, shell syntax, helper-code syntax, indentation, code-block formatting, markdown escaping, escape characters, non-literal examples, or copied command exactness must not block PF09 completion planning, phase handoff, QA readiness, implementation readiness, or PF09 row supportability.

PF09 readiness depends on task truth, implementation supportability, evidence supportability, phase fit, scope authority, safety, acceptance posture, and evidence identity. Syntax defects in plan text do not prevent a PF09 row from being supportable to Done unless they expose a separate truth, proof, scope, authority, safety, acceptance, phase, or evidence-identity defect.

If a QA operator, Codex, Kronos, PO, implementation owner, reviewer, or technical writer encounters a non-runnable command, escaped string, indentation defect, heredoc issue, shell syntax issue, or helper-code formatting issue during execution or review, they may normalize it in flight as long as the proof target, QA step identity, scope boundary, rails posture, evidence intent, acceptance posture, public/private boundary, no-secret posture, no-new-token posture, and no-new-scope posture remain unchanged.

Before raising an escape-character, syntax, command, or paste-readiness blocker for a PF09 task ID, subtask ID, path, token, artifact key, command, environment variable, heading, proof line, plan step, or review prompt, inspect the raw phase document, raw governed artifact, raw repo file, Human Evidence Index binding, Machine Mirror record, or path-proof transcript. Display-layer artifacts and plan-syntax concerns must not block supportable-from-repo-evidence language, later-drain posture, redline placement, status interpretation, phase handoff, or QA readiness.
