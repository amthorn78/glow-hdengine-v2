## **Precedence, versioning, and scope**

### **1\. PF10 authority**

PF10 IS CANONICAL. For any topic explicitly addressed by an applicable, active PF10 addendum, that addendum is the current authoritative source of truth and supersedes conflicting permanent PF canon until the guidance is formally reviewed and drained into the relevant permanent PF document.

No competing canon may be used against an applicable PF10 addendum. Agents must not prefer, merge, reinterpret, or reconcile conflicting permanent-canon language while the PF10 guidance remains active.

PF10 authority is limited to the scope actually addressed by its addenda. The presence of a topic elsewhere in a PF10 document does not make PF10 authoritative over related topics that no addendum addresses.

### **2\. Scope within an individual PF10 document**

An individual PF10 document is a container for multiple numbered addenda. It must not be treated as one undifferentiated rule or as blanket authority over every topic associated with the current epic.

Each addendum is an independent unit of authority with its own scope. That scope is established by the addendum’s heading and substantive content, including the decisions, requirements, exceptions, artifacts, behaviors, processes, or canon topics it explicitly addresses.

Within one PF10 document:

1. Every active, non-superseded addendum remains authoritative for its own stated scope.  
2. A higher-numbered addendum does not automatically invalidate every lower-numbered addendum in the document.  
3. Unrelated addenda remain independently authoritative and must be applied together when more than one is relevant to the current task.  
4. An addendum must not be applied outside the scope established by its actual content.  
5. The entire document must be searched for relevant addenda. Agents must not consult only the first, last, or highest-numbered addendum.  
6. Document-level relevance does not establish addendum-level relevance. An agent must identify which specific addendum or addenda govern the current question.

For example, if addendum `2.12` governs evidence indexing and addendum `2.18` governs compatibility routing, both remain authoritative within their separate scopes. The existence of `2.18` does not supersede `2.12` merely because `2.18` has a higher number.

### **3\. Single-document and multi-document PF10 versions**

An active PF10 base version may consist of either:

1. One unlettered document, such as `10.x.x`; or  
2. One multi-document lettered set, such as `10.x.xa`, `10.x.xb`, `10.x.xc`, and so forth.

A lettered set may be used when an epic’s build notes exceed the practical capacity of one document and drainage before the end of the epic is not practical.

All documents sharing the same base version and carrying sequential letter suffixes belong to the same PF10 version set. For example:

* `10.x.xa`  
* `10.x.xb`  
* `10.x.xc`

Together, these documents constitute the complete active `10.x.x` PF10 set.

The letter suffix identifies a physical document within the set. It does not create a newer base version, determine topical scope, or give one document greater authority than another.

All documents in the active lettered set are equally authoritative containers of PF10 addenda. A later lettered document extends the set. It does not replace, obsolete, drain, or supersede an earlier lettered document merely because it has a later suffix.

For example, `10.x.xb` does not replace `10.x.xa`. Active, non-superseded addenda in both documents remain authoritative for their respective scopes.

### **4\. Continuous addendum sequence**

A lettered PF10 set must preserve one continuous addendum-number sequence across all documents in the set.

Each subsequent lettered document must begin with the addendum number immediately following the final addendum in the preceding document.

Example:

* `10.x.xa` contains addenda through `2.28`.  
* `10.x.xb` begins with addendum `2.29`.  
* If `10.x.xb` ends with addendum `2.41`, `10.x.xc` begins with addendum `2.42`.

The numbered addendum sequence establishes the order of PF10 guidance. The document-letter sequence identifies where that guidance is stored.

### **5\. Individual-addendum supersession**

Supersession operates at the individual-addendum level, not automatically at the document level.

This rule applies:

* Between addenda in the same individual PF10 document.  
* Between addenda located in different documents within the same lettered PF10 set.

Each addendum remains authoritative for its stated scope unless a higher-numbered addendum revises, replaces, narrows, expands, or otherwise supersedes that scope.

When two or more addenda address the same or overlapping scope:

1. The highest-numbered applicable addendum is the sole authority for the overlapping scope.  
2. Conflicting or replaced language in every lower-numbered addendum is superseded and must not be applied in parallel.  
3. A lower-numbered addendum remains authoritative for any distinct scope not superseded by the higher-numbered addendum.  
4. If the higher-numbered addendum explicitly supersedes the earlier addendum in full, no portion of the earlier addendum remains authoritative.  
5. Supersession applies regardless of whether the addenda appear in the same document or in different documents within the active lettered set.

Example within one document:

* Addendum `2.17` establishes a rule.  
* Addendum `2.22` in the same document revises that rule.  
* Addendum `2.22` controls the revised scope.  
* Addendum `2.17` remains authoritative only for any distinct scope that `2.22` does not supersede.

Example across a lettered set:

* Addendum `2.17` appears in `10.x.xa`.  
* Addendum `2.34` appears in `10.x.xb` and revises the same rule.  
* Addendum `2.34` controls the overlapping scope.  
* Addendum `2.17` must not be used as competing or parallel authority for that scope.  
* Any distinct portion of addendum `2.17` not superseded by `2.34` remains authoritative.

A later document letter alone supersedes nothing. Addendum number and addendum scope determine supersession.

### **6\. Current-version rule**

Only the latest active PF10 base version matters. That version may be represented by one unlettered document or by a complete lettered set.

Older base versions are fully drained, obsolete, or both. Once a newer base version exists, agents must not read, reuse, compare, reconcile, or carry forward content from an older base version.

This rule does not apply between documents belonging to the same active lettered set. If `10.x.xa`, `10.x.xb`, and `10.x.xc` form the active version, all three remain part of the authoritative PF10 source set.

An earlier lettered document remains authoritative for every applicable addendum it contains that has not been superseded by a higher-numbered addendum. It must not be discarded merely because a later lettered document exists.

### **7\. Live-content rule**

The active PF10 document or complete lettered set contains the current live guidance that has not yet been drained into its permanent PF home.

Drained guidance is removed when PF10 is formally revised.

If a lower-numbered addendum remains physically present after a higher-numbered addendum supersedes some or all of its scope, the superseded language is no longer live authority. Physical presence does not defeat individual-addendum supersession.

All unaffected, non-superseded addenda within the same document or lettered set remain live and authoritative for their respective scopes.

### **8\. Silence rule**

PF10 governs only through applicable, active, non-superseded addenda.

PF10 is silent when no addendum in the complete active PF10 document or lettered set addresses the current topic.

When PF10 is silent, authority returns to the relevant permanent PF-Canon document.

PF10 silence must be determined only after checking:

1. Every potentially relevant addendum within each applicable individual document.  
2. Every document belonging to the complete active lettered set, when a lettered set exists.  
3. Any higher-numbered addendum that may have superseded earlier guidance.

### **9\. Operational rule for agents**

Agents must apply PF10 in this order:

1. Identify the latest active PF10 base version.  
2. Determine whether it consists of one unlettered document or a multi-document lettered set.  
3. If it is a lettered set, identify all documents sharing that base version, such as `10.x.xa`, `10.x.xb`, and `10.x.xc`.  
4. Treat each document as a container of separately scoped numbered addenda.  
5. Search every applicable document for all addenda relevant to the current topic.  
6. Determine the actual scope of each relevant addendum from its heading and substantive content.  
7. Compare the scopes of all relevant addenda, including addenda within the same document.  
8. Where addendum scopes overlap, apply only the highest-numbered applicable addendum to the overlapping scope.  
9. Continue applying lower-numbered addenda to any distinct scope not superseded by a higher-numbered addendum.  
10. Do not infer document-level supersession from a later letter suffix.  
11. Ignore all older PF10 base versions.  
12. Fall back to permanent PF canon only when the complete active PF10 document or lettered set contains no applicable, active, non-superseded guidance for the topic.

### D-3 — POST /api/compat/v1 is a dev/admin surface (S19-R03)

Decision.

* Classification. The compat namespace, /api/compat/v1 and its descendants, is a dev/admin-only surface under HDE Governance §4.1.4. HDE CLI/API/Vendor Ref §5.5 already calls the route "dev only", "development-only" and "internal admin".  
* Gate order. On every method, before any compat computation, database read or vendor call:  
  * Production-like posture, as §5.5 resolves it, keeps its current response. That posture is prod, production or live, read from trimmed, case-folded nonempty APP\_ENV, otherwise ENGINE\_ENV. The response is 404, error\_v1 with code=ERR\_NOT\_FOUND, and Cache-Control: no-store; HEAD carries no body.  
  * Any other request is served only when APP\_ENV is exactly dev, test or local, with no trimming, no case-folding and no default.  
    * A missing, empty or other value refuses with the writer-style refusal the dev/admin HTTP surfaces use: ERR\_WRITER\_FORBIDDEN, status 403, Cache-Control: no-store, no ETag, and no body on HEAD.  
    * ENGINE\_ENV never admits the surface.  
  * The existing method, probe and POST rules of §5.5 apply.  
* Authentication.  
  * No credential is required while the surface is admitted only under APP\_ENV exactly dev, test or local. This matches every other dev/admin surface under §4.1.4.  
  * §5.5's "authenticated" and "internal authentication" are withdrawn: no mechanism exists in canon or code.  
* Wider exposure. Before the compat route is served in any other environment, a later decision must:  
  * require the HDE Governance §8.3.2 admin credential, or an equivalent credential pinned in HDE CLI/API/Vendor Ref;  
  * add the §8.3.4 logging rules.  
* Residual risk, accepted and recorded.  
  * A dev, test or local process connected to the shared production database serves stored-user compat results to whoever reaches its port. The Staging/QA HD Engine is a GitHub Codespace on that database (Glow Infrastructure §2.2), with APP\_ENV=dev (§2.4).  
  * That exposure is controlled by where the process listens, the documented loopback access of Glow Infrastructure §2.2, not by this route. It is the same posture as every other dev/admin surface.

Basis.

* HDE Governance controls authority and permissions (Change Process Guide §0.1A). Its §4.1.4 rule is explicit:  
  * dev/admin surfaces "MUST" allow exactly dev, test and local;  
  * they "MUST NOT assume a default".  
* The current guard refuses only production-like values (engine/http/compat\_handler.py line 112). adapter/env\_guard.py::\_compute\_env\_mode returns dev when both variables are unset, and passes staging and unknown values through (lines 31 to 51). So the route serves unauthenticated results in exactly the cases §4.1.4 forbids.  
* Gating closes that with a rule canon already states and a gate the code already has (adapter/http\_reader.py lines 901 to 907).  
* A credential for a dev-only route (options B and C) adds secret, transport and rotation machinery that removes no exposure once the gate holds. HDE-COAG006.5 scopes that machinery to admin bundles, and this decision does not widen that subtask.

## 2.2 Planning documents and PF-Canon versions are never inputs; the close-pack writer runs only at close

Timestamp: 102826 06:25 (UTC). Details: Records the Product Owner's architecture direction of 2026-10-28 that planning documents serve planning only, that PF-Canon document versions may change at any time, and that the close-pack writer runs only at the end of a full work-unit cycle. It states three rules, the defect that prompted them, what was changed to conform, and the items that do not yet conform.

### Decision and approval status

* Decision. The Product Owner directed, on 2026-10-28, that it was an architecture mistake for anything to rely on ephemeral files or to pin anything to a PF version, that ephemeral files are only for planning, that PF document versions may change at any time, and that the close-pack generator runs only at the end of a full work-unit cycle. Rules R-1 to R-3 below state that direction as canon.  
* Status. Proposed. The rules take effect as canon when this addendum is published in HDE Build Notes.  
* Relation to other canon. HDE Governance keeps the role of in-flight documents in docs/ephemeral/ for the planning, authoring, review and decisions of their own change. This addendum governs what may depend on those documents and on PF-Canon file identities. Where HDE Governance, HDE Schemas & Artifacts, Change Process Guide, Glow QA Guide or HDE Mechanics Guide require a close pack, tool, test or record to read or bind a planning document, or to name a PF document by file name or version, this addendum supersedes that requirement for that scope.

### The defect that prompted it

* HDE-CRD-0002's close pack bound seven planning documents under docs/ephemeral/ and its implementation plan as causal inputs, and the close-pack writer re-read them in check mode. When those documents were archived out of the repository, the committed close pack could no longer be checked on main.  
* The writer resolved the CRD register and the Build Checklist registers by versioned PF file name, and the writer's test copied two versioned PF files from the checkout. When the HDE CRD Records document changed version, the test failed on main for every pull request that ran it.  
* The writer's test ran as part of full-validation CI, so a planning-document archive or a PF version change turned unrelated pull requests red.

### R-1 — Planning documents serve planning only

* A planning document is any change-process work product stored under docs/ephemeral/: Specifications, Plans, instructions, reviews, reports, RCAs, readiness records, dispositions, handoffs and result records.  
* No code, test, tool, CI step, workflow, schema, governed evidence artifact, close pack, manifest, Index or Mirror row or path proof reads, binds, hashes, resolves or requires a path under docs/ephemeral/. A test builds any document it needs as its own fixture.  
* A fact a later stage needs from a planning document is recorded where that stage reads it, when it is recorded: for a close pack, in the close-candidate source, as a record text naming the document's identity and SHA-256, and as the structured facts the writer checks (requirement IDs, QA plan checks and their mapped criteria, the QA verdict).  
* A prose citation of a planning document in a permanent record is a reference only. Archiving or deleting the cited document invalidates nothing that depends on the record.

### R-2 — PF-Canon is resolved by stable identity, never by version

* PF-Canon document versions, and therefore file names, may change at any time.  
* No code, test, tool, CI step, schema, governed artifact or committed record that must remain valid pins a PF document's file name, version or content digest, or requires its bytes to stay unchanged.  
* A tool that needs current canon resolves the document at the time it runs, by PF identity and versionless title, to the one current file under docs/pfcanon/, and refuses when that resolution is not unique. Validation of an already committed artifact does not re-read canon.  
* A citation of canon in code, a test, a tool, an ADR or a governed artifact names the PF document by title, and its section where needed. HDE Build Notes is cited by title alone, without an addendum number, because its addendum numbers restart with each base version.

### R-3 — The close-pack writer runs only at close

* The close-pack writer writes a close pack only at the close stage, at the end of a full work-unit cycle, after the authorized QA verdict and the closure decision exist.  
* The writer's test is a close-stage test. CI selects it when the writer, a close-candidate source schema, the closeout validation workflow or the test itself changes. It is not part of full validation or of any other ordinary required pull-request CI (Plan Templates, "CI lane classification and automated budget-control discipline").

### Changes delivered with this record

These changes are carried by the pull request that carries this record. They are completed work, not further obligations.

* Close-pack writer. A v2 close-candidate source records planning\_records (identity and SHA-256 of the Specification, implementation plan, QA plan and final QA report), requirement\_ids, qa\_checks and qa\_verdict, and has no plan path or planning-document binding. No path under docs/ephemeral/ or docs/pfcanon/ is a causal input, pointer or key output in either schema version (PLANNING\_OR\_CANON\_INPUT\_PROHIBITED). A deferral's drain target names its register by PF title. PF titles and register headings are resolved at write time only, by title, against the canon tracked at HEAD; check mode reads no PF-Canon file. A later-drain statement and a superseded artifact may name a planning document by record text.  
* Close-pack test. Every v2 fixture is built in the test's own repository, including the PF-Canon file names and registers; no test reads the checkout's docs/ephemeral/ or docs/pfcanon/. Tests that parsed real planning documents are removed with the parsing they tested. New tests prove that check mode passes after the canon changes version or is removed, and that a planning or canon path is refused as an input or pointer.  
* CI classification. The close-pack test is the one close-stage test. Full validation no longer selects it; a change to the writer, a close-candidate schema, the closeout validation workflow or the test does. The roster invariants and the pre-push coverage sweep count it as reached.  
* ADR. The close-pack writer ADR is amended to record this direction and to reverse the earlier Product Owner decisions that bound the writer to planning documents and versioned PF file names.  
* HDE-CRD-0002 close pack. The candidate source is rebuilt from the archived planning documents; their recovered bytes match the SHA-256 digests the earlier close pack recorded. The writer regenerated the close report and manifest, and the canonical evidence updater republished their Mirror rows and path proofs. The close-run family under audit/qa/hde-crd-0002/close/ is unchanged and remains the record of the close run of 2026-10-26.
