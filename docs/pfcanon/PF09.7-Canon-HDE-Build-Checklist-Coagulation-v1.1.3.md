## **0.1 Scope** 

This phase covers solidification into durable production form. From a software development perspective, Coagulation is where the refined product is locked into a dependable operating posture: runtime image and startup behavior are made reproducible, environment and secrets discipline are enforced, production-facing transport and ops surfaces are hardened, and the release can stand as a stable service rather than an evolving build candidate. From a planning perspective, this document should track the work that turns proven behavior into institutionalized runtime confidence, including deployment posture, startup proof, env discipline, ops surfaces, and evidence that supports durable closure. It is not the place for exploratory scope or soft definitions of readiness; the concern here is stable operation, explicit operational posture, and a production form that can hold.

The phase model and the rule against mixing alchemical modes are governed by **PF21 \- 7 Phases of Alchemical Engineering**. This document applies that model to its named phase and must not absorb work merely because the work is related to an existing task.

## **0.2 PF09 Purpose, Eligibility, and Exclusions**

PF09 is the canonical, dependency-ordered register of phased product-development and operations work required to build and maintain the Glow HDE system. Each PF09 document contains only work belonging to its named alchemical phase.

A task or subtask belongs in PF09 only when it is part of the phased HDE product build, requires development or operations engagement, and produces or changes at least one of the following:

* application, engine, CLI, transport, harness, or tooling code;  
* automated tests or reproducible verification behavior;  
* runtime configuration, deployment behavior, or migration behavior;  
* infrastructure, access-control, secret-management, or other operator-controlled state;  
* schemas, interfaces, or machine-readable artifacts used by implementation;  
* required executable evidence demonstrating the behavior of an in-scope change; or  
* removal, consolidation, or migration of an existing implementation surface.

PF09 excludes standalone documentation-only and process-only work, including:

* PF-Canon wording changes without corresponding phased development or operations work;  
* ADR, template, prompt, playbook, or guidance maintenance;  
* `AGENTS.md` or other instruction-file maintenance;  
* historical reports, summaries, or retrospective evidence inventories;  
* standalone evidence-ledger rows;  
* board administration; and  
* QA planning or QA execution that does not itself require development of a harness, test, or operational capability.

Documentation or evidence required by an in-scope task may appear as a deliverable or acceptance requirement within that task. It must not become a separate PF09 task solely because documentation or evidence must be recorded.

## **0.3 Task, Status, and Deferral Conventions**

### **Status values**

PF09 uses only these task and subtask statuses:

* **Done:** The required behavior is implemented for the stated scope, and the evidence and decisions required for that scope are established.  
* **Partial:** Some, but not all, required behavior, verification, evidence, or decisions are established. Notes must identify the remaining gap.  
* **Not done:** Required behavior, implementation, verification, evidence, or decisions remain absent.  
* **Consolidation pending:** Applicable behavior exists in multiple slices but must be consolidated before the task can be treated as Done.  
* **Optional:** Non-blocking work that is not required for the applicable release, epic, or phase gate.

A deferred item retains an allowed status, normally **Not done** or **Optional**, and records the deferral in Notes:

`DEFERRED → <future epic or backlog reference> — <reason>; not a close blocker for <current epic>.`

Deferred work must not be represented as satisfied or completed.

### **Repository support versus PF09 status**

Repository evidence and PF09 status are separate facts.

Use:

* `Supportable from repository evidence:` when current evidence supports a status change that has not yet been recorded in PF09.  
* `Drained into PF09:` only when the PF09 status has actually been updated.

Repository evidence does not silently mutate PF09. An existing PF09 status does not override contradictory current repository reality.

### **Tracking identifiers**

Tasks use `HDE-<PHASE><NNN>`.

Subtasks use `HDE-<PHASE><NNN>.<m>`.

Tracking identifiers are stable traceability labels. They do not imply priority, lifecycle state, acceptance, or completion.

Each new task must identify, as applicable:

* task ID and name;  
* purpose and intended behavior;  
* phase placement;  
* owner or execution lane;  
* deliverables;  
* dependencies and sequencing;  
* implementation or integration boundary;  
* verification properties;  
* required evidence;  
* status; and  
* unresolved limitations or deferrals.

## **0.4 Authority and Work-Record Routing**

PF09 governs:

* whether phased HDE implementation or operations work is tracked;  
* the phase in which that work belongs;  
* task decomposition and dependency order;  
* task status; and  
* the task-level implementation and verification burden.

PF09 does not independently redefine mechanics, governance, change process, QA semantics, schemas, evidence formats, artifact contracts, or planning templates owned by other authoritative documents.

Use the current controlling sources for their respective lanes:

* **PF03 \- Technical Writing Best Practices:** source fidelity, complete-source use, claim posture, canonical ownership, and documentation structure.  
* **PF04 \- HDE Governance:** authority, exact-source acceptance, claim discipline, exceptions, and evidence-policy consequences.  
* **PF05 \- HDE CLI, API, and Vendor Reference:** exact CLI, API, transport, public-byte, and vendor-facing contracts.  
* **PF06 \- Change Process Guide:** epic and CRD lifecycle, mutation routes, execution, acceptance, drainage, and closure process.  
* **PF12 \- HDE Schemas and Artifacts:** governed schemas, manifests, evidence indexes, mirrors, hashes, path proofs, and artifact integrity.  
* **PF14 \- HDE Mechanics Guide:** implementation mechanics and evidence-producing behavior.  
* **PF19 \- Glow QA Guide:** QA planning, execution, evidence, verdicts, and revalidation.  
* **PF21 \- 7 Phases of Alchemical Engineering:** phase meanings, phase order, and the rule against mixing alchemical modes.  
* **PF23 \- Reality Audits:** Product Owner post-epic reality-audit records that agents may read as historical planning context but do not schedule, trigger, or satisfy.  
* **PF27 \- Plan Templates:** reusable plan, runbook, review, operations, and closeout structures.

Plans and record documents are execution indexes. They must identify controlling requirements and evidence without reproducing large portions of their owning canon.

### **Epic and CRD boundary**

* Epic work that belongs to the phased HDE product build is tracked through the applicable PF09 task or subtask.  
* CRD-originated work is tracked through PF30 and must not be duplicated in PF09 merely because it uses development, pull request, QA, operations, or closure lanes similar to an epic.  
* A CRD may cause separate phased product work to be added or mapped to PF09 only through an explicit authorized decision. Until that decision is recorded, PF30 remains the work-record authority for the CRD.  
* A CRD that changes canon requires an accompanying ADR, applicable Build Notes activity, and later drainage into the affected permanent canon. The canon edit is not itself a PF09 implementation task.  
* PF09 and PF30 record different authorized work populations. Neither document silently creates, transfers, closes, or updates work in the other.

## **0.5 Evidence and Legacy References**

PF09 consumes the current exact-source, governed-artifact, QA, and operations rules from their owning documents. A PF09 task must define its required behavior, verification properties, evidence burden, and decision dependencies precisely enough for planning, but it must not reproduce complete schemas, path catalogs, QA runbooks, or repository-mutation procedures.

Existing acceptance-token references in historical PF09 rows are compatibility metadata only. Preserve their spelling and historical meaning, but do not issue replacement tokens, require token ceremony, infer current PASS from them, or treat them as proof. Evaluate the underlying requirement through current exact-source evidence and authorized decisions.

## **0.6 Completion Standard**

A PF09 task may be recorded as **Done** only when:

* its required behavior is implemented for the stated scope;  
* dependencies required for that scope are satisfied;  
* applicable tests or verification properties pass against the identified implementation state;  
* required governed evidence is complete and internally consistent;  
* required QA, operations, or acceptance decisions are confirmed separately;  
* unresolved failures, limitations, or deferrals are disclosed; and  
* an authorized PF09 update records the resulting status.

No commit, branch, PR, workflow run, artifact hash, historical token, agent assertion, or single decision independently proves all completion conditions. Completion is a scoped lifecycle determination supported by the applicable combination of current repository facts, exact-source evidence, governed artifacts, and authorized decisions.

### **Subtask HDE-COAG001.5 — Optional production caching**

*Subtask name/label:* Private Reader cache (optional)

*Subtask description:*

If a production cache is used, provide a **private, composite-key cache** for Reader and Compat that preserves A7 transport rules and deterministic invalidation:

**Composite key (keys-only).**

Use a composite cache key of the form:

`{viewer_id | person_id(s)}, design_fingerprint, thresholds_identity, release_id`.

Normalize `{a,b}` pairs to a stable order before keying (AB↔BA neutrality) so that compat/Reader responses for `(A,B)` and `(B,A)` hit the same cache entry.

Include `viewer_id` in the key **only** when cacheable output depends on viewer preferences (e.g. perspective); otherwise, omit it so that the same content is shared across viewers.

**Deterministic key construction.**

Key construction must be pure and reproducible:

No dependence on clocks, randomness, or ambient environment state.

Derived only from the normalized inputs and identity fields listed above (titles-only to Mechanics/Math for design\_fingerprint and thresholds\_identity semantics).

**A7-consistent transport behavior.**

Cache hits must preserve full A7 semantics for the success route:

200: `Content-Type: application/json; charset=utf-8`; strong, quoted ETag over the LF-terminated body (pre-compression); `Cache-Control: private, max-age=0, must-revalidate`; `Vary: Authorization, Accept-Encoding`.

304: only after a prior 200 for the same ETag; no body; omit `Content-Type` and `Content-Length`; validators mirror the cached 200; ETag present.

HEAD: status 200; no body; validators mirror 200; `Content-Type == GET`; `Content-Length == len(identity 200 body)`.

Writers and errors **bypass** the cache and continue to send `Cache-Control: no-store` with **no ETag**; cached paths must not alter typed error envelopes.

`/internal/version` is never cached.

**Deterministic invalidation.**

Invalidate cache entries immediately on any change to:

`release_id`,

`thresholds_identity`,

design/manifest identity (design\_fingerprint or pack/manifest identity), or

input payloads that affect the response (including viewer\_prefs when present).

Once invalidated, no stale bytes may be served; cache re-populates only via fresh emissions under the same A7 posture.

**Controls & diagnostics.**

Default **OFF**: the production cache is disabled by default and may be enabled **only** via a documented runtime flag or configuration toggle; PF09 does not pin the flag name or config path.

Metrics:

Emit **bounded** counters for cache hits, misses, and invalidations (labels such as `route`, `outcome`, `rails_state`, `timeout_profile`), reusing the global observability/metrics discipline.

Optional diagnostics:

When enabled for debugging, maintain a redaction-safe, keys-only debug log of cache decisions (hits/misses/invalidation) suitable for local analysis; routes, IDs, and state are logged via bounded labels only; no raw payloads or secrets may appear.

PF09 does not define cache internals, SLO thresholds, or diagnostics log paths; those remain single-homed in Governance, Mechanics, and infra/ops docs. This subtask records that, when a production cache is present, it obeys composite-key, determinism, A7-consistent transport, deterministic invalidation, metrics, and optional diagnostic logging as described above.

*Subtask status:* Not done

*Epic or card:* Unknown

*Tokens:* (unchanged; semantics live in Governance; PF09 routes by title only)

*Evidence / artifacts:* (unchanged; cache behavior is supported by existing A7 and parity/observability evidence from other phases)
