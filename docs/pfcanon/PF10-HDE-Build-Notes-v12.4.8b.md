## **Precedence, versioning, and scope**

### **1\. PF10 authority**

PF10 IS CANONICAL. For any topic explicitly addressed by an applicable, active PF10 addendum, that addendum is the current authoritative source of truth and supersedes conflicting permanent PF canon until the guidance is formally reviewed and drained into the relevant permanent PF document.

No competing canon may be used against an applicable PF10 addendum. Agents must not prefer, merge, reinterpret, or reconcile conflicting permanent-canon language while the PF10 guidance remains active.

PF10 authority is limited to the scope actually addressed by its addenda. The presence of a topic elsewhere in a PF10 document does not make PF10 authoritative over related topics that no addendum addresses.

### **2\. Scope within an individual PF10 document**

An individual PF10 document is a container for multiple numbered addenda. It must not be treated as one undifferentiated rule or as blanket authority over every topic associated with the current epic.

Each addendum is an independent unit of authority with its own scope. That scope is established by the addendum’s heading and substantive content, including the decisions, requirements, exceptions, artifacts, behaviors, processes, or canon topics it explicitly addresses.

Within one PF10 document:

1. Every active, non-superseded addendum remains authoritative for its own stated scope.  
2. A higher-numbered addendum does not automatically invalidate every lower-numbered addendum in the document.  
3. Unrelated addenda remain independently authoritative and must be applied together when more than one is relevant to the current task.  
4. An addendum must not be applied outside the scope established by its actual content.  
5. The entire document must be searched for relevant addenda. Agents must not consult only the first, last, or highest-numbered addendum.  
6. Document-level relevance does not establish addendum-level relevance. An agent must identify which specific addendum or addenda govern the current question.

For example, if addendum `2.12` governs evidence indexing and addendum `2.18` governs compatibility routing, both remain authoritative within their separate scopes. The existence of `2.18` does not supersede `2.12` merely because `2.18` has a higher number.

### **3\. Single-document and multi-document PF10 versions**

An active PF10 base version may consist of either:

1. One unlettered document, such as `10.x.x`; or  
2. One multi-document lettered set, such as `10.x.xa`, `10.x.xb`, `10.x.xc`, and so forth.

A lettered set may be used when an epic’s build notes exceed the practical capacity of one document and drainage before the end of the epic is not practical.

All documents sharing the same base version and carrying sequential letter suffixes belong to the same PF10 version set. For example:

* `10.x.xa`  
* `10.x.xb`  
* `10.x.xc`

Together, these documents constitute the complete active `10.x.x` PF10 set.

The letter suffix identifies a physical document within the set. It does not create a newer base version, determine topical scope, or give one document greater authority than another.

All documents in the active lettered set are equally authoritative containers of PF10 addenda. A later lettered document extends the set. It does not replace, obsolete, drain, or supersede an earlier lettered document merely because it has a later suffix.

For example, `10.x.xb` does not replace `10.x.xa`. Active, non-superseded addenda in both documents remain authoritative for their respective scopes.

### **4\. Continuous addendum sequence**

A lettered PF10 set must preserve one continuous addendum-number sequence across all documents in the set.

Each subsequent lettered document must begin with the addendum number immediately following the final addendum in the preceding document.

Example:

* `10.x.xa` contains addenda through `2.28`.  
* `10.x.xb` begins with addendum `2.29`.  
* If `10.x.xb` ends with addendum `2.41`, `10.x.xc` begins with addendum `2.42`.

The numbered addendum sequence establishes the order of PF10 guidance. The document-letter sequence identifies where that guidance is stored.

### **5\. Individual-addendum supersession**

Supersession operates at the individual-addendum level, not automatically at the document level.

This rule applies:

* Between addenda in the same individual PF10 document.  
* Between addenda located in different documents within the same lettered PF10 set.

Each addendum remains authoritative for its stated scope unless a higher-numbered addendum revises, replaces, narrows, expands, or otherwise supersedes that scope.

When two or more addenda address the same or overlapping scope:

1. The highest-numbered applicable addendum is the sole authority for the overlapping scope.  
2. Conflicting or replaced language in every lower-numbered addendum is superseded and must not be applied in parallel.  
3. A lower-numbered addendum remains authoritative for any distinct scope not superseded by the higher-numbered addendum.  
4. If the higher-numbered addendum explicitly supersedes the earlier addendum in full, no portion of the earlier addendum remains authoritative.  
5. Supersession applies regardless of whether the addenda appear in the same document or in different documents within the active lettered set.

Example within one document:

* Addendum `2.17` establishes a rule.  
* Addendum `2.22` in the same document revises that rule.  
* Addendum `2.22` controls the revised scope.  
* Addendum `2.17` remains authoritative only for any distinct scope that `2.22` does not supersede.

Example across a lettered set:

* Addendum `2.17` appears in `10.x.xa`.  
* Addendum `2.34` appears in `10.x.xb` and revises the same rule.  
* Addendum `2.34` controls the overlapping scope.  
* Addendum `2.17` must not be used as competing or parallel authority for that scope.  
* Any distinct portion of addendum `2.17` not superseded by `2.34` remains authoritative.

A later document letter alone supersedes nothing. Addendum number and addendum scope determine supersession.

### **6\. Current-version rule**

Only the latest active PF10 base version matters. That version may be represented by one unlettered document or by a complete lettered set.

Older base versions are fully drained, obsolete, or both. Once a newer base version exists, agents must not read, reuse, compare, reconcile, or carry forward content from an older base version.

This rule does not apply between documents belonging to the same active lettered set. If `10.x.xa`, `10.x.xb`, and `10.x.xc` form the active version, all three remain part of the authoritative PF10 source set.

An earlier lettered document remains authoritative for every applicable addendum it contains that has not been superseded by a higher-numbered addendum. It must not be discarded merely because a later lettered document exists.

### **7\. Live-content rule**

The active PF10 document or complete lettered set contains the current live guidance that has not yet been drained into its permanent PF home.

Drained guidance is removed when PF10 is formally revised.

If a lower-numbered addendum remains physically present after a higher-numbered addendum supersedes some or all of its scope, the superseded language is no longer live authority. Physical presence does not defeat individual-addendum supersession.

All unaffected, non-superseded addenda within the same document or lettered set remain live and authoritative for their respective scopes.

### **8\. Silence rule**

PF10 governs only through applicable, active, non-superseded addenda.

PF10 is silent when no addendum in the complete active PF10 document or lettered set addresses the current topic.

When PF10 is silent, authority returns to the relevant permanent PF-Canon document.

PF10 silence must be determined only after checking:

1. Every potentially relevant addendum within each applicable individual document.  
2. Every document belonging to the complete active lettered set, when a lettered set exists.  
3. Any higher-numbered addendum that may have superseded earlier guidance.

### **9\. Operational rule for agents**

Agents must apply PF10 in this order:

1. Identify the latest active PF10 base version.  
2. Determine whether it consists of one unlettered document or a multi-document lettered set.  
3. If it is a lettered set, identify all documents sharing that base version, such as `10.x.xa`, `10.x.xb`, and `10.x.xc`.  
4. Treat each document as a container of separately scoped numbered addenda.  
5. Search every applicable document for all addenda relevant to the current topic.  
6. Determine the actual scope of each relevant addendum from its heading and substantive content.  
7. Compare the scopes of all relevant addenda, including addenda within the same document.  
8. Where addendum scopes overlap, apply only the highest-numbered applicable addendum to the overlapping scope.  
9. Continue applying lower-numbered addenda to any distinct scope not superseded by a higher-numbered addendum.  
10. Do not infer document-level supersession from a later letter suffix.  
11. Ignore all older PF10 base versions.  
12. Fall back to permanent PF canon only when the complete active PF10 document or lettered set contains no applicable, active, non-superseded guidance for the topic.

## 2.30) PF10 Scope Model: Independently Scoped Addenda and Lettered Multi-Document Version Sets

Timestamp: 072726 20:40  
Details: This addendum records the Product Owner’s modification of the PF10 scope and versioning policy. It clarifies authority within an individual PF10 document and establishes a lettered multi-document structure for cases in which one document cannot practically contain all live build notes for an epic and drainage before the epic ends is not practical.

### **Decision summary**

PF10 authority operates at the level of individually scoped addenda.

An active PF10 base version may be represented by either:

1. One unlettered document; or  
2. One complete lettered document set.

A lettered document set is one logically continuous PF10 version divided across multiple physical documents. All documents in that set are equally authoritative containers of independently scoped addenda.

Supersession continues to operate at the individual-addendum level. A later document letter does not supersede an earlier document. A higher-numbered addendum supersedes a lower-numbered addendum only for overlapping scope or where the later addendum explicitly supersedes the earlier guidance.

### **PF10 authority**

PF10 remains canonical for every topic explicitly addressed by an applicable, active, non-superseded PF10 addendum.

For that topic, the applicable PF10 addendum supersedes conflicting permanent PF canon until the guidance is formally reviewed and drained into its permanent PF home.

No competing canon may be used against applicable PF10 guidance. Agents must not prefer, merge, reinterpret, or reconcile conflicting permanent-canon language while that PF10 guidance remains active.

PF10 authority does not extend beyond the scope actually established by its addenda.

### **Scope within an individual PF10 document**

An individual PF10 document is a container of separately numbered and separately scoped addenda. It must not be treated as one undifferentiated rule or as blanket authority over every topic associated with the current epic.

Each addendum is an independent unit of authority. Its scope is established by its heading and substantive content, including the decisions, requirements, exceptions, artifacts, behaviors, processes, or canon topics it explicitly addresses.

Within an individual PF10 document:

1. Every applicable, active, non-superseded addendum remains authoritative for its own scope.  
2. A higher-numbered addendum does not automatically supersede every lower-numbered addendum.  
3. Unrelated addenda remain independently authoritative.  
4. Multiple addenda must be applied together when they govern separate aspects of the same task.  
5. An addendum must not be extended beyond the scope established by its actual content.  
6. Document-level relevance does not establish that every addendum in the document is relevant.  
7. Agents must identify the specific addendum or addenda applicable to the current question.  
8. Agents must not consult only the first, last, or highest-numbered addendum.

For example, if addendum `2.12` governs evidence indexing and addendum `2.18` governs compatibility routing, each remains authoritative for its separate scope. Addendum `2.18` does not supersede addendum `2.12` merely because it has a higher number.

The authority of an individual PF10 document is therefore the combined authority of all applicable, active, non-superseded addenda it contains.

### **Individual-addendum supersession**

Supersession operates at the individual-addendum level.

This rule applies both:

1. Between addenda in the same PF10 document; and  
2. Between addenda in different documents belonging to the same lettered PF10 set.

When two or more addenda address the same or overlapping scope:

1. The highest-numbered applicable addendum is the sole authority for the overlapping scope.  
2. Conflicting or replaced language in every lower-numbered addendum is superseded and must not be applied in parallel.  
3. A lower-numbered addendum remains authoritative for any distinct scope not superseded by the higher-numbered addendum.  
4. If a higher-numbered addendum explicitly supersedes an earlier addendum in full, no portion of the earlier addendum remains authoritative.  
5. Supersession applies regardless of which document in a lettered set contains either addendum.

Example within one document:

* Addendum `2.17` establishes a rule.  
* Addendum `2.22` revises part of that rule.  
* Addendum `2.22` is the sole authority for the revised scope.  
* Addendum `2.17` remains authoritative only for any distinct scope not superseded by addendum `2.22`.

A higher addendum number establishes later sequence. It does not establish broader scope. Later-addendum precedence applies only after the addenda are determined to address the same or overlapping scope.

### **Single-document PF10 version**

A PF10 base version may initially consist of one unlettered document, represented generically as:

* `10.x.x`

That document contains all numbered addenda belonging to the active PF10 version.

The document remains subject to the individual-addendum scope and supersession rules above. The highest-numbered addendum does not replace unrelated lower-numbered addenda within the document.

### **Lettered multi-document PF10 set**

When an epic’s live build notes exceed the practical capacity of one document and drainage before the end of the epic is not practical, the active PF10 base version may be divided into a sequential lettered set.

Generic examples are:

* `10.x.xa`  
* `10.x.xb`  
* `10.x.xc`

All documents sharing the same base version and carrying sequential letter suffixes belong to one PF10 version set.

Together, `10.x.xa`, `10.x.xb`, and `10.x.xc` constitute the complete active `10.x.x` PF10 version.

The suffix identifies a physical document within the set. It does not:

* create a newer base version;  
* establish a separate authority tier;  
* determine topical scope;  
* give a later document greater authority;  
* drain an earlier document;  
* obsolete an earlier document; or  
* supersede any addendum merely because it appears in a later document.

Every document in the active lettered set is equally authoritative as part of the same PF10 version.

For example, `10.x.xb` extends the set containing `10.x.xa`. It does not replace `10.x.xa`. Applicable, active, non-superseded addenda in both documents remain authoritative for their respective scopes.

### **Continuous addendum numbering**

A lettered PF10 set must preserve one continuous addendum-number sequence across every document in the set.

Each subsequent lettered document must begin with the addendum number immediately following the final numbered addendum in the preceding document.

Example:

* `10.x.xa` ends with addendum `2.28`.  
* `10.x.xb` begins with addendum `2.29`.  
* If `10.x.xb` ends with addendum `2.41`, `10.x.xc` begins with addendum `2.42`.

Addendum numbers must not restart when a new lettered document begins.

The numbered addendum sequence establishes the order of PF10 guidance. The document-letter sequence identifies where that guidance is physically stored.

### **Supersession across a lettered set**

Individual-addendum supersession continues without interruption across document boundaries.

Example:

* Addendum `2.17` appears in `10.x.xa`.  
* Addendum `2.34` appears in `10.x.xb` and revises the same rule.  
* Addendum `2.34` controls the overlapping scope.  
* Addendum `2.17` must not be used as competing or parallel authority for that scope.  
* Any distinct portion of addendum `2.17` not superseded by addendum `2.34` remains authoritative.

The result is caused by the relationship between addenda `2.17` and `2.34`, not by the relationship between document letters `a` and `b`.

A later document letter alone supersedes nothing.

### **Current-version rule**

Only the latest active PF10 base version matters.

The latest base version may be represented by:

1. One unlettered document; or  
2. One complete lettered document set.

Older PF10 base versions are fully drained, obsolete, or both. Agents must not read, reuse, compare, reconcile, or carry forward guidance from an older base version once a newer base version exists.

This prohibition does not apply between documents belonging to the same active lettered set.

If `10.x.xa`, `10.x.xb`, and `10.x.xc` constitute the active base version, all three remain part of the authoritative PF10 source set. An earlier lettered document remains authoritative for every applicable addendum it contains that has not been superseded by a higher-numbered addendum.

The phrase “only the latest PF10 file matters” must therefore be understood as “only the latest PF10 base version matters.” When the latest base version is a lettered set, the complete set matters.

### **Live-content rule**

The active PF10 document or complete lettered set contains live guidance that has not yet been drained into its permanent PF home.

Drained guidance is removed when PF10 is formally revised.

If a lower-numbered addendum remains physically present after a higher-numbered addendum supersedes some or all of its scope, the superseded language is no longer live authority. Physical presence does not defeat individual-addendum supersession.

Any unaffected portion of that addendum remains authoritative unless it has also been drained or superseded.

All unrelated, non-superseded addenda within the same document or lettered set remain live and authoritative for their respective scopes.

### **Silence rule**

PF10 governs only through applicable, active, non-superseded addenda.

PF10 is silent when no such addendum in the complete active PF10 version addresses the current topic.

When PF10 is silent, authority returns to the relevant permanent PF-Canon document.

PF10 silence must be determined only after checking:

1. Every potentially relevant addendum within the applicable individual document;  
2. Every document belonging to the active lettered set, when a lettered set exists; and  
3. Every higher-numbered addendum that may have superseded earlier guidance.

### **Required agent procedure**

Agents applying PF10 must:

1. Identify the latest active PF10 base version.  
2. Determine whether that base version consists of one unlettered document or a lettered document set.  
3. If it is lettered, identify every document belonging to that set, such as `10.x.xa`, `10.x.xb`, and `10.x.xc`.  
4. Treat each document as a container of separately scoped numbered addenda.  
5. Search the complete active document or set for every addendum relevant to the current topic.  
6. Determine the actual scope of each relevant addendum from its heading and substantive content.  
7. Compare the scopes of all relevant addenda, including addenda contained in the same document.  
8. Apply all independently relevant addenda together.  
9. Where addendum scopes overlap, apply only the highest-numbered applicable addendum to the overlapping scope.  
10. Continue applying lower-numbered addenda to any distinct scope not superseded by a higher-numbered addendum.  
11. Never infer document-level supersession from a later letter suffix.  
12. Ignore all older PF10 base versions.  
13. Fall back to permanent PF canon only when the complete active PF10 document or set contains no applicable, active, non-superseded guidance for the topic.

### **Effect on existing PF10 language**

This addendum supersedes the existing statement that “only the latest PF10 file matters” only to the extent that the statement requires or implies one physical PF10 document.

The controlling rule is now:

* Only the latest PF10 base version matters.  
* If that base version is a lettered set, every document in that set matters.  
* Within the active document or set, authority remains divided among independently scoped addenda.

This addendum also qualifies the existing “later addendum wins” rule.

The controlling interpretation is now:

* A higher-numbered addendum controls overlapping or explicitly superseded scope.  
* A higher-numbered addendum does not supersede unrelated lower-numbered addenda.  
* A lower-numbered addendum remains authoritative for distinct scope not superseded by later guidance.

All other existing PF10 authority, live-content, permanent-canon fallback, and older-version obsolescence rules remain unchanged.

### **Standing integration requirement**

The policy established by this addendum must be incorporated into **HDE Build Notes**, §Purpose and §Precedence and versioning, when the standing PF10 description is next revised.

That revision must preserve:

* independently scoped authority within each individual PF10 document;  
* individual-addendum supersession;  
* partial supersession limited to overlapping scope;  
* equal document authority within a lettered set;  
* continuous addendum numbering across the set;  
* the distinction between a document suffix and a base version;  
* the complete-set requirement for agent consultation;  
* older-base-version obsolescence; and  
* permanent-canon fallback when the complete active PF10 version is silent.

A later PF10 revision must not silently drop this policy when making the current PF10 version obsolete.

### **Present effect and non-effects**

This policy is effective immediately.

This addendum establishes the permitted lettered-set model. It does not itself:

* divide the current PF10 into multiple documents;  
* create or rename any PF10 document;  
* declare that the current PF10 has exceeded its practical capacity;  
* drain any existing addendum;  
* change the substantive scope of any unrelated addendum;  
* alter any PF09 status;  
* modify the development board;  
* authorize repository mutation;  
* authorize OPS or QA execution;  
* establish acceptance; or  
* close an epic.
