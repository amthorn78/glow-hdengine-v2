## 6. Exact required behavior

### 6.1 Admitted input classes and identity resolution

Three input classes remain distinct (Plan §5.8):

1. **Already-resolved chart with existing trusted engine identity/provenance.** Carry the resolver/DB `user_id` and canonicalize its UUID spelling; an admitted internal engine alias goes through the existing `resolve_db_user_id` bridge before canonicalization. Cross-check every supplied identity slot against its provenance; conflicting identities refuse. Preserve the complete mapped BodyGraph, not just type or Gates. A complete file/stdin projection needs no vendor or DB lookup. A chart lacking both identity provenance and a complete sanctioned birth tuple is missing required internal metadata; do not invent identity from Gates.
2. **Existing stored-user / admin lookup.** Resolve the admitted engine user key with `resolve_db_user_id`, then `str(UUID(resolved_id))`, and use that canonical value for the parameterized lookup and application identity. Use the actual read-only lookup (`_fetch_db_bodygraph` or the existing injected local lookup), carrying payload plus verified row identity and source metadata. Resolver status, UID or cache metadata alone is not a chart. Validate a hit; an invalid hit fails rather than being hidden by a vendor fallback.
3. **Complete birth-only / no-user input** — birthdate, birthtime and location per party, with no caller `person_uid`, `user_id` or app ID. Validate the existing birth input contract, reuse `_derived_birth_uid`'s existing `birth-` seed unchanged, pass that seed through `resolve_db_user_id`, and canonicalize the returned UUID. This is the existing internal durability-alias bridge inside the sanctioned resolver — not a public identity requirement and not a claim that an application user exists. Try the permitted local lookup for that internal key first; a verified complete hit may succeed with network rails closed and with no user-row creation. On an allowed miss, acquire a complete chart through the guarded existing route per §6.2. **A birth input or derived UUID alone never produces Gates, type, scores or a successful compat result.**

`resolve_db_user_id` may return noncanonical UUID spelling, so the application adapter normalizes and validates the final RFC-4122 UUID before creating an `EvaluationParty`. The existing `person-…` label is display/provenance metadata and is never accepted literally as a canonical UUID; where a mapped chart uses it, check matching top-level and nested labels and the trusted resolver context that created them before binding the application copy to the resolved canonical UUID. Do not strip a prefix and assume ownership, override an independently conflicting identity, use the CLI's generic fallback UID, or derive identity from Gate masks. Contradictory charts under the same resolved identity take the inconsistent-self failure path. Separately supplied trusted identities for distinct people are preserved even when their masks coincide.
